# Комплексный рефакторинг ИСМПУ: единый контур управления, телеметрия, матрица прогонов, PID-дашборд и SFT

## 1. Подтверждённые проблемы и целевое состояние

Подтверждены основные проблемы:

- Ложный XTE вызван тем, что `Telemetry.from_ics()` подставляет курс UUEE‑06R `75°`. Из-за этого стендовые `RunwayHeading=64°` и `LateralDeviation≈0` игнорируются, а геодезический fallback вычисляет ложные 4–26 м; найдено значение 9,52 м, совпадающее с наблюдением.
- Производственный запуск разделён: `working_ics` управляет заходом, затем `VlaydRolloutBridge` создаёт второй контроллер для земли. Общего жизненного цикла, RunRecorder и полной телеметрии нет.
- Существуют два дашборда:
  - эталонный [working_ics/dashboard.py](C:/GOSNIIASProject/ismpu/working_ics/dashboard.py) — рабочая live-шкала, инкрементальная выдача точек и настройка воздушных PID;
  - основной [gui/dashboard.py](C:/GOSNIIASProject/ismpu/gui/dashboard.py) — девять представлений и безопасная очередь изменений, но он не подключён к реальному production entrypoint и имеет дефекты live/replay.
- Основной дашборд каждые 500 мс передаёт весь буфер всех представлений, дублирует сбор данных отдельно от RunRecorder, смешивает величины разных размерностей на одной шкале, копирует Pitch в Flare и неполно воспроизводит CSV `working_ics`.
- [RunRecorder](C:/GOSNIIASProject/ismpu/runtime/run_recorder.py) хранит прогон в RAM до завершения, пишет только часть 99 входных полей ICS, неизвестные новые поля теряются, `working_ics` вообще не пишет наземную часть в тот же журнал.
- Сценарии, коэффициенты и сокращённая копия Excel-матрицы смешаны: 890 строк `scenarios.py`, 346 строк вручную перенесённой матрицы, при этом часть исходного текста и различий между 280 прогонами потеряна.
- Текущий SFT захватывает данные непосредственно через RL-среду, работает только с пятью наземными PID и использует модель с PPO-критиком и вероятностными головами, которые для регрессии не нужны.
- Baseline тестов: 409 проходят, 2 пропущены, 10 падают. Последний стендовый лог подтверждает актуальный переход `Approach → Landing` на 25 ft, поэтому старый тест на 40 ft считается устаревшим.

Целевая цепочка:

```text
ICS/X‑Plane
    → IcsPacket/Telemetry
    → ControllingSystem.step(telemetry, dt)
    → ApproachController | GroundController
    → ControlStep
    → RunRecorder + Dashboard
    → ControlCommand
    → backend
```

Runtime единолично отвечает за приём, запись и отправку. Контроллеры не читают UDP, не отправляет команды и не пишут файлы.

Нормативные критерии берутся непосредственно из ТЗ, приложения по критичности и исходной Excel-матрицы, без пересказа порогов в нескольких модулях.

## 2. Ключевые интерфейсы

- `Telemetry` остаётся единственным нормализованным кадром. Поля становятся validity-aware; невалидный сигнал представлен `None`, а не правдоподобным нулём.
- `IcsPacket` содержит timestamp, адрес, исходный UTF‑8 JSON, полный словарь, типизированный `ICSInputs`. Неизвестные поля сохраняются в raw-журнале.
- `ControllingSystem.step(telemetry, dt) -> ControlStep` запрошенная и фактически отправленная команда, сегмент, режим, guidance, диагностика, состояния PID, allocator, события и признак завершения; I/O из него удаляется.
- `PidSample`: value, setpoint, error, Kp/Ki/Kd, P/I/D, integral, unclamped/output/applied, saturation.
- `RunSample`: один неизменяемый снимок такта. Именно его получает RunRecorder и показывает dashboard; отдельная интроспекция контроллера из GUI удаляется.
- `GuidanceState` дополняется источником (`bench`/`geodetic`), XTE, отдельными course/heading errors и опциональным along-track.
- `MatrixRun` представляет одну из 280 строк Excel с устойчивым `matrix_run_id=<шифр>/<номер>`. Фактический запуск получает отдельный `execution_id`.`Scenario` только комбинирует выбранные строки для `APPROACH`, `ROLLOUT`, `TAXI`.
- `DashboardSnapshot`: метаданные прогона, только новые кадры после `sequence`, события, текущая revision коэффициентов и описание доступных PID.
- `GroundControlConfig` и `ApproachConfig` хранят базовую настройку шифра плюс необязательный override конкретного `run_id`; эффективная конфигурация всегда материализуется целиком.
- `RunRecorder.record(packet, telemetry, control_step, transmitted_output)` получает данные явно, без `getattr`-интроспекции внутренних объектов.
- `GainChange`: request ID, ожидаемая revision, сегмент, PID, старые и новые коэффициенты. Применяется runtime в начале следующего такта.
- `GainCandidate`: полный effective config выбранного сегмента, связанный с execution ID, matrix hash и итоговым отчётом.

### Этап 1 — Исправить границу телеметрии и ложный XTE

- Удалить безусловную подстановку `runway_heading_true_deg=75` из ICS-кадра.
- При `RunwayHeadingValid=1` использовать пару `RunwayHeading + LateralDeviation`; для курсового сравнения использовать `TrkAngleMagnetic`. `MagneticHeading` сохранять как отдельную проверку ориентации корпуса.
- Геодезический fallback разрешать только при валидных координатах, true track/heading и явно выбранном профиле ВПП. Отсутствие обоих источников приводит к безопасной нейтрали и диагностическому событию, а не к выдуманной оси.
- Не смешивать магнитные и истинные направления.
- Добавить параметр знака `LateralDeviation` в профиль стенда; начальное значение `+1`, подтверждение выполняется статическим стендовым тестом ±смещение.
- При отсутствии обоих источников формировать нейтральную команду и событие `guidance_unavailable`.
- Разделить диагностику на `xte`, `course_error`, `heading_error`, `guidance_error`, `along_track` и `source`.
- Проверять validity скоростей, координат, ориентации, высот и ILS до использования.
- Записывать все 99 известных полей ICS и все неизвестные raw-поля, но включать в закон управления только обоснованные сигналы.
- Исправить потребителей `along=None`: наземное наблюдение использует пройденную интегральную дистанцию, а не `runway_length - None`.
- Добавить replay-тест реального кадра: при `RunwayHeading=64°`, `LateralDeviation=0` команда поворота должна быть около нуля независимо от координат UUEE.

Критерий: кадр с `RunwayHeading=64°` и `LateralDeviation=0` даёт XTE и steering command около нуля независимо от координат UUEE; ложные 4–26 м исчезают; прямой и геодезический источники никогда не смешиваются молча.

### Этап 2 — Пересобрать наземный контроллер

Добавить только диагностику и опциональный tracking фактически применённой команды. Численность воздушного контура проверяется golden parity.

- Разделить латеральную ошибку на XTE, course error и итоговую guidance error; логировать каждый член до PID, выход PID, насыщение и вклад в каждый актуатор.

- Логировать профиль скорости, пройденную дистанцию, ускорение, ошибку скорости и состояния четырёх продольных PID.
- Ввести явные команды: rudder, pedal, tiller, left/right brake, left/right reverse.

### Этап 5 — Единая телеметрия, replay и отчётность

Каждый запуск создаёт:

```text
runs/<run-id>/
├── manifest.json
├── raw-rx.jsonl
├── raw-tx.jsonl
├── telemetry.csv
├── approach.csv
├── ground.csv
├── events.jsonl
├── candidates/
└── report.json
```

- Runtime создаёт один `RunSample` после каждого такта.
- `raw-rx.jsonl` сохраняет точный UDP JSON до фильтрации, включая неизвестные новые поля; `raw-tx.jsonl` — фактически отправленные пакеты.
- `telemetry.csv` содержит полный полёт, все известные входы/выходы, validity, SI-представление, raw-значения, timestamps, `dt`, сегмент, control mode/mask, config revision и ID сценария.
- `approach.csv` содержит воздушные признаки, три PID, их состояния, ILS, flare, envelope, цели, ошибки и команды.
- `ground.csv` содержит rollout/taxi, пять PID, guidance-разложение, speed profile, allocator и actuator feedback.
- `events.jsonl` фиксирует handshake, режимы, касание, отказы, dropout, смену конфигурации/gains, saturation, fallback и завершение.
- Запись идёт append-only с flush раз в секунду; при аварии теряется не более одного буфера. Накопление всего полёта только в RAM исключается.
- В памяти остаётся только ограниченный ring buffer для live-dashboard.
- `manifest.json` содержит git revision/dirty flag, backend, профиль ВС, hash матрицы, выбранные строки, полные эффективные конфиги, единицы, частоту, schema version и stop reason.
- Ошибка записи не должна снимать управление: прогон помечается `recording_failed`, dashboard показывает ошибку, результат запрещается принимать/SFT.
- `RunReader` обслуживает и replay, и dashboard. Для прежних main/working CSV остаётся один compatibility adapter; отсутствующие P/D-поля показываются как недоступные, а не восстанавливаются выдуманными значениями.
- Replay выполняет контроллер без отправки UDP и сравнивает команды и диагностику по каждому `tick_id`, `sequence`.
- Отчёт рассчитывает критерии соответствующей строки: максимальные отклонения, touchdown, speed profile, время/дистанцию, задержку после отказа, насыщения и диагностику среды.
- Команда агрегации формирует `matrix-results.csv`, совместимый с результатными столбцами исходной книги.

### Этап 6 — Объединить и расширить PID-дашборд

#### 6.1. Один dashboard вместо двух

- Каноническим становится `ismpu/gui`; production не импортирует dashboard из `working_ics`.
- Из эталона `working_ics` переносятся:
  - инкрементальный протокол `since`;
  - `run_id` и сброс timeline при новом прогоне;
  - режим Live и просмотр прошлого момента;
  - окна 30/60/120 секунд и полный прогон;
  - sliders и немедленное отображение текущих gains;
  - удержание dashboard после завершения.
- Из основной реализации сохраняются:
  - loopback-only сервер;
  - monitor-only по умолчанию;
  - очередь изменений с применением только на границе control tick;
  - replay и экспорт.
- Не добавлять WebSocket, frontend framework или новую зависимость: один static HTML/canvas и stdlib HTTP server покрывают задачу.

#### 6.2. Единый источник данных

- `DashboardState.capture()` и повторная интроспекция PID удаляются.
- Dashboard получает те же `RunSample` и `RunEvent`, которые пишет RunRecorder.
- `GET /api/state?since=<sequence>&run_id=<execution-id>` возвращает только новые кадры и события.
- Если новых кадров нет, ответ остаётся постоянного небольшого размера.
- HTTP-поток никогда не блокирует и не изменяет контроллер напрямую.
- Live и replay используют одинаковый `DashboardSnapshot`; replay отличается только read-only режимом.

#### 6.3. Представления

Сохраняются девять представлений для восьми уникальных PID:

- Air: Roll, Pitch, Flare, Air Speed.
- Ground: Steer, Brake L/R, Reverse L/R.
- Flare использует Pitch PID, но показывает только flare-фазу; вне неё значения не копируются как активный flare-контур.
- Для каждого PID отображаются три синхронных графика с отдельными шкалами:
  1. value/setpoint/error;
  2. requested/output/applied/feedback;
  3. P/I/D/integral/saturation.
- Это исключает текущую ошибку общей шкалы, на которой малые PID-компоненты исчезают рядом со скоростью или углом.

Дополнительные панели:

- Header: backend, execution/matrix IDs, профиль ВС, segment, control mode/mask, config revision, частота цикла, возраст телеметрии, AgentIsActive, recorder status.
- Air overview: LOC/GS, RA, IAS/VAPP, VS/target, attitude/rates, flare, throttle/thrust, envelope/tolerance.
- Ground lateral: bench XTE, geodetic fallback, выбранный источник, track/heading/course errors, steering output и вклад allocator в каждый орган.
- Ground longitudinal: groundspeed/reference, distance, acceleration, базовые и смешанные brake/reverse команды и feedback.
- Telemetry: все 99 известных ICS-полей с единицами и validity, а также отдельная группа неизвестных raw-полей; поиск и группировка без включения всех сигналов в управление.
- Matrix/config: выбранные строки сегментов, expected/actual conditions, effective config, статус draft/tuned/accepted.
- Events: handshake, mode transitions, flare, touchdown, gain changes, failures, saturation, fallback и завершение.
- После внедрения SFT: static/predicted/effective gains и причина GainGuard/fallback; модель из dashboard не редактируется.

#### 6.4. Безопасная настройка коэффициентов

- Редактировать можно только PID активного сегмента в режимах `classical` и `sft-shadow`.
- В `sft-active` коэффициенты соответствующего сегмента доступны только для чтения.
- Диапазоны и шаг sliders приходят с сервера из конфигурации; hardcoded JS-диапазоны удаляются.
- Воздушные начальные диапазоны переносятся из рабочего dashboard; наземные — из gain-space/config.
- POST создаёт `GainChange` со старой revision и возвращает `202 pending`.
- Runtime применяет изменение в начале следующего такта. При смене сегмента устаревший запрос отклоняется.
- Изменение выполняется bumpless: сохраняются derivative history и текущий выход, integral корректируется в допустимых пределах; actuator slew limits остаются последней защитой.
- Каждое применение, отклонение и возврат записываются в `events.jsonl` с before/after, временем, sequence, segment и matrix ID.
- Кнопка Revert возвращает run-start effective gains через ту же очередь.

#### 6.5. Candidate → promotion

Выбрана безопасная политика сохранения:

- Dashboard не меняет канонические scenario/config-файлы.
- `Save candidate` пишет полный effective config в `candidates/<segment>-<revision>.json`.
- После завершения команда promotion проверяет:
  - успешность и приёмочный отчёт;
  - совпадение execution, matrix и config hashes;
  - отсутствие recorder/telemetry errors;
  - replay команд.
- Только после проверки создаётся sparse override соответствующей строки и статус `tuned`.
- Статус `accepted` выставляется после прохождения полного обязательного набора условий.
- Неудачный прогон и несохранённое изменение никогда не попадают в конфигурации или SFT.

Критерий этапа: live и replay показывают одни и те же значения; dashboard покрывает воздух и землю, не влияет на частоту контура и не создаёт третий канал телеметрии.

### Этап 7 — Настройка классики по матрице

Порядок кампании:

1. Б.1.1/У.1: знак XTE, курс, торможение и плавность касания.
2. Остальные условия Б.1.1.
3. Б.1.2 — прямое taxi.
4. Б.2.* — NWS и перераспределение.
5. Б.3.* — реверс/тяга.
6. А.1.* на рабочем воздушном контуре.
7. А.2–А.4 с профильными overrides.
8. Б.4.* — сквозная приёмка.

Для каждого прогона сохраняются applied gains, saturation, feedback, effective config и нормативный отчёт.

- Dashboard меняет только текущий override; каждое изменение gains записывается по времени.
- После удачного прогона сохраняется полный effective config, а не только изменённые поля.
- Приёмочные пороги берутся из конкретной строки и нормативных документов: ±3 м rollout, ±1 м straight taxi, ±5 м при NWS, курс ±5° при thrust/reverse до 30 уз, курсовой/глиссадный допуск, touchdown speed/sink/load и диагностика сцепления, ветра и аквапланирования.
- Конфигурация получает `accepted` только после прохождения своего набора условий; неудачный прогон не попадает в SFT.

### Этап 8 — Два независимых SFT-регрессора

- Создать один минимальный `PidGainRegressor` — `LayerNorm → однослойный GRU → Linear`; использовать два независимых экземпляра:
  - air: 3 PID × `kp/ki/kd` = 9 выходов;
  - ground: 5 PID × `kp/ki/kd` = 15 выходов.
- Выходы — абсолютные PID-коэффициенты.
- Удалить из активного SFT critic, `log_std`, PPO-loss, channel weights и прямые actuator outputs. PPO-код оставить изолированным и не импортировать runtime.
- Модели выдают только абсолютные коэффициенты. Цели — фактически применённые expert gains из принятого прогона.
- Формировать датасеты офлайн из `approach.csv` и `ground.csv`; live-стенд не является частью обучения.
- Окно по умолчанию — 40 кадров/2 секунды, прогноз обновляется каждый такт 20 Гц после заполнения окна.
- Воздушные признаки: ILS, RA, скорости, attitude/rates, runway/track, flare, механизация, thrust/throttle feedback, ветер, отказы и PID state.
- Наземные признаки: XTE/course/heading, speed/reference/acceleration, yaw/side acceleration, runway/weather, WOW, actuator feedback, отказы, дистанция/время и PID state.
- Текущие `kp/ki/kd` исключаются из входа, чтобы сеть не училась просто копировать их.
- Разбиение train/validation/test выполняется по целым прогонам и условиям; окна одного полёта не попадают в разные выборки.
- Нормализованная регрессия использует MSE; gate по умолчанию: MAE ≤5% и p95 ≤10% диапазона каждого коэффициента, а также результат лучше постоянного baseline.
- Чекпоинты раздельные: `sft_air.pt`, `sft_ground.pt`; каждый хранит feature schema/hash, gain layout, normalization, matrix hash, список run IDs и метрики.
- Общий `GainGuard` применяется перед PID:
  - finite/OOD check;
  - физические границы и диапазон `0.3–2.5 ×` accepted preset;
  - предел изменения `25%` preset в секунду с учётом фактического `dt`;
  - fallback на accepted static preset при dropout, неполном окне, ошибке модели или нарушении контракта.
- Режимы запуска: `classical` по умолчанию, `sft-shadow`, `sft-active`. Воздушная и наземная модели включаются независимо.
- Активация на ICS разрешается только после replay, X‑Plane и shadow-прохождения без ухудшения критериев относительно статической классики.

### Этап 9 — Завершение миграции

- Удалить из активного кода bridge, дубли схемы протокола, недостижимые entrypoints, ручную матрицу и live-capture через `RolloutEnv`.
- `working_ics` сохранить неизменяемым эталоном; production не зависит от него.
- RL/PPO оставить вне рабочего runtime и документации текущей кампании, без дальнейшего развития.
- ICS и X‑Plane используют одинаковые controller, scenario, telemetry, recorder и dashboard; различаются только transport/reset.
- Обновить документацию запуска, dashboard, настройки матрицы, candidate/promotion, схемы артефактов, replay и SFT.

## 4. Тестирование и критерии готовности

- Полный тестовый набор зелёный.
- Golden parity воздуха с `working_ics`: PID, команды, режимы и wire JSON.
- Golden-паритет воздуха с `working_ics` выполняется до `1e-12`, а wire-последовательность режимов совпадает.
- Golden parity dashboard: четыре воздушных представления, timeline, gains и incremental sequence.
- Один UDP-сеанс проходит от включения до завершения земли без второго handshake.
- Реальный XTE regression: `64°/0 м` не создаёт поворот.
- Segment tests: Approach → Landing 25 ft → Rollout → Taxi/Off, bounce не возвращает управление в воздух.
- Ground tests: знаки, allocator, saturation, NWS/reverse/thrust failures, completion rules.
- Recorder tests: все известные поля, неизвестные raw-поля, сегментные CSV, crash/flush и ошибка writer.
- Dashboard API tests: monitor-only, loopback-only, invalid/NaN gains, stale revision, очередь, segment switch и SFT locks.
- Live/replay equality: каждый PID и plotted signal совпадает для одного `RunSample`.
- Нагрузочный тест: 10 минут × 20 Гц; incremental API не пересылает историю повторно и dashboard не блокирует control tick.
- Candidate tests: неуспешный прогон не promotion; успешный создаёт только override своей строки.
- Matrix tests: ровно 280 строк, 156 air и 124 ground, точное соответствие Excel.
- SFT tests: отсутствие leakage, reproducible training, checkpoint contract, continuous prediction и fallback.
- Стендовый acceptance: один UDP-сеанс от 10 NM до завершения наземного участка, единая телеметрия и отсутствие ложного XTE.
- Все 280 строк Excel представлены и адресуются отдельно; для любой композиции воспроизводится полный effective config.
- Классические конфигурации проходят свои критерии до обучения.
- Два SFT-чекпоинта обучаются только на принятых прогонах, работают непрерывно по окну и fail-safe возвращаются к статическим PID.
- Криволинейный маршрут до конкретного парковочного места остаётся вне этого рефакторинга; поддерживается прямой taxi по маршруту/XTE стенда.

## 5. Зафиксированные допущения

- ICS — production backend; X‑Plane — resettable test/evaluation backend.
- Частота контура — 20 Гц.
- Стендовые runway heading/deviation имеют приоритет над геодезией.
- `working_ics` не удаляется и не становится runtime-зависимостью.
- Настроенные gains сохраняются по схеме candidate → проверяемый promotion.
- Для матричных наземных прогонов требуется полная остановка, кроме Б.1.2; нематричный handover выполняется при 7,5 kt.
- Маршрут с поворотами до конкретного парковочного места не входит в этот рефакторинг; поддерживается прямое taxi по заданному XTE/маршруту.
- PPO/RL отложены; текущий нейросетевой объём ограничен двумя SFT-регрессорами.
